# Протокол воспроизведения и новых испытаний

## Повторный расчёт старой серии

Из корня репозитория выполните команды быстрого запуска из README. Контрольный набор в `results/reference` не изменяется. Результаты собственной обработки сохраняются в `results/local/legacy`. Для старого генератора доступен `python scripts/legacy_gen.py --selector S1 --run 1 --out results/local/gt.csv`; отправлять трафик разрешается только после подготовки своего учебного стенда.

## Подготовка нового стенда

Зафиксируйте модели, версии ПО, MTU, аппаратное ускорение, маршруты и конфигурации. Для серий B–E перенесите P=192.168.20.10 с Loopback Cisco на отдельный конечный узел. Нельзя одновременно оставлять этот адрес на двух устройствах. Настройте обратные маршруты и согласованные селекторы обоих шлюзов.

Для проверок доставки N1/N2/E1/E2 также должны обозначать действующие конечные службы. Разместите внешний сервер за ER-ISP и устраните конфликт адресов с прежними Loopback. Реальные адреса задаются JSON-таблицей по образцу `examples/targets.json`.

## Порядок и общий профиль

```bash
python extensions/schedule.py --seed NET074-v2 --out results/local/schedule.csv
python extensions/traffic_v2.py plan --seed block-01 --profile equal --count 1000 --targets examples/targets.json --out results/local/plan01.json
```

Предварительно создайте папку `results/local`, если она отсутствует. В Ubuntu: `mkdir -p results/local`; в PowerShell: `New-Item -ItemType Directory -Force results/local`.

Один plan используется для S1/S2/S3 внутри блока. В следующем блоке меняется seed. Каждая попытка имеет новый acquisition ID; журналы не перезаписываются. Schedule содержит 15 блоков, каждый селектор занимает каждую из трёх позиций по 5 раз. Это баланс позиций, а не полное устранение всех эффектов предыдущего испытания.

## Приёмники и захваты

На каждом конечном узле с открытой UDP-службой запустите приёмник. Пример для P:

```bash
python extensions/traffic_v2.py serve --bind 192.168.20.10 --port 50074 --duration 120 --out P_receiver.jsonl
```

Захваты начните до генератора. Нужны точки до шифрования у A, оба WAN, LAN после расшифрования у B, P и внешний сервер. Для Linux-точки:

```bash
bash extensions/capture.sh eth0 /absolute/path/pre.pcap 90
```

Выберите фактический интерфейс. Сохраните stderr tcpdump и счётчики потерь захвата. На шлюзах используйте средства monitor/зеркалирования, проверенные для точных моделей и версий ПО. После смены селектора проверьте реальные SA и negotiated selectors; перед каждым прогоном сохраняйте SPI и счётчики, повторяйте снимок после него. Если нужная SA или точка захвата не подтверждена, прогон помечается недействительным.

## Генератор и сверка

```bash
python extensions/traffic_v2.py send --plan results/local/plan01.json --bind 192.168.10.100 --source-port 40074 --rate 200 --out results/local/S1_B01_sender.jsonl
python extensions/validate_v2.py --sent results/local/S1_B01_sender.jsonl --received P_receiver.jsonl N1_receiver.jsonl N2_receiver.jsonl E1_receiver.jsonl E2_receiver.jsonl --pre pre.pcap --post post_B.pcap post_E.pcap --out results/local/packet_validation.json
```

Включите все журналы открытых служб и все соответствующие post-PCAP. В сценарии закрытого порта приложения-приёмника намеренно нет; отсутствие echo не считается измеренной потерей рабочей службы. Успех sendto означает передачу ядру ОС. Без журнала приёмника потеря равна null, а не 0 %. Проверяйте полноту журналов и ненулевые показатели missing, unexpected, duplicates и mismatch.

`validate_v2.py` сверяет независимые открытые UDP-наблюдения и журналы, но не извлекает внутреннее содержимое ESP. При равных длинах разных классов внешняя классификация сохраняет unknown. IPv6, NAT-корреляция и сборка фрагментов не реализованы. PCAPNG предварительно преобразуйте `editcap -F pcap input.pcapng output.pcap`.

## Сетевые сценарии

| Серия | Условие | Что зафиксировать |
| --- | --- | --- |
| A | P на Loopback Cisco, UDP закрыт | Источник и открытая цитата локальной ICMP-ошибки |
| B | P за Cisco, UDP закрыт | Источник ошибки P и её обработка шлюзами |
| C | P за Cisco, UDP открыт | Приём, echo, RTT, прямой и обратный пути |
| D | Ошибку создаёт транзитный Cisco | TTL exceeded/недоступность и цитируемый пакет |
| E | B/D после точечной меры | Раскрытие, доставка, диагностика и PMTU до/после |

Не выключайте ICMP целиком для получения «успешного» результата. Применимость выбранной меры должна подтверждаться для конкретной версии шлюза, включая Fragmentation Needed и крупные TCP-передачи. Для внешнего сервера нужны отдельные TCP- и UDP-тесты; изменение пути и отказ службы регистрируются раздельно.

## Полноценный аудит и независимая истина

Обе сравниваемые процедуры получают одинаковые политику, конфигурации обоих шлюзов, SA, счётчики, маршруты, PCAP и конечные журналы. Полный аудит тоже анализирует вложенные заголовки ICMP. Эталонные события задаются заранее и размечаются независимо от ответов автоматического метода.

CSV истины: `event_id,truth`; CSV предсказаний: `event_id,prediction`. Допустимы truth=0/1 и prediction=0/1/unknown.

```bash
python extensions/score_audit.py --truth truth.csv --prediction full_audit.csv --out results/local/baseline_score.json
python extensions/score_audit.py --truth truth.csv --prediction method.csv --out results/local/method_score.json
```

Оценщик считает бинарное обнаружение нарушений. Для назначения класса каждого пакета нужна отдельная многоклассовая матрица P/N1/N2/E1/E2/unknown; этот скрипт её не заменяет. Неизвестные положительные события включаются в нижнюю границу recall. Покрытие и метрики по определённым решениям сообщаются вместе. Время ручного и автоматического анализа измеряется на одном и том же наборе и одинаковом оборудовании.

## Производительность

Проведите отдельные нагрузочные серии с общим планом, прогревом и измерительным окном не менее 60 секунд, превышающим период усреднения CPU. Снимайте CPU обоих шлюзов и фиксируйте телеметрию, частоту опроса, фон и аппаратное ускорение. Для максимальной пропускной способности нужна ступенчатая нагрузка до насыщения.

Goodput рассчитывается по уникальным полезным байтам приёмника за объявленное окно, потери UDP — по независимым ID. Дубликаты, ошибки sendto и потери механизма захвата учитываются отдельно. RTT измеряется на одних часах клиента. Встроенный echo_goodput_bps включает grace между sender_start и sender_stop и не является предельной производительностью VPN.
